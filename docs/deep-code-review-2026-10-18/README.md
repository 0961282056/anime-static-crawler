## Findings

### P2：主來源重新爬取可覆寫已有來源的簡介，或遺失出處

位置：`services/data_repository.py` 的 `DataRepository.write_quarter()`（修正後215–234行）。

觸發條件：同一作品身分重新從主來源爬取，傳入基礎記錄沒有集數enrichment、沒有`story_source`，但`story`非空。舊程式只在傳入簡介為「暫無簡介」時保留已有來源的簡介。因此來源提供不同文字時，會替換先前逐筆核對的內容並丟失出處；即使文字恰好相同，也會清掉`story_source`。官方介紹及Bangumi已查證原文都會經過此路徑。這違反既有「補入不得覆蓋已存在簡介、保留原文與出處」要求。

修復：在作品身分未改變的基礎來源刷新中，若原資料有`story_source`、傳入記錄沒有新證據，則保留舊簡介與完整出處，無論傳入文字空白、相同或不同。一般未附查證出處的主來源介紹仍可照原流程更新；帶有明確新`story_source`的更正仍會經模型與身分保護驗證後寫入。既有ID衝突／卡片消失／版本變動／人工範圍保護不變。

證據：官方／Bangumi各搭配「同文／異文」四個案例，修正前全部失敗；修正後全通過。另有正向案例驗證帶新出處的更正可正常寫入。

### P2：持久待辦只比較本文，未同步Issue開關狀態

位置：`services/review_queue.py` 的 `_save_queue()`（修正後81–90行）。

觸發條件：待辦payload沒變，但系統待辦Issue被手動關閉／重開。舊程式看到本文相同就直接返回，可能讓非空待辦保持closed，或已空的待辦維持open。待辦證據仍存在，但狀態與實際未通知工作數不一致，會讓維護者看到錯誤的待辦狀態。

修復：以payload計算期望狀態，只有本文和狀態都一致才跳過更新。需要校正時只同步系統Issue，不新增審核通知；校正完成後再次執行不會重複PATCH。未改指定審核者A/B/C、日期提醒或公開資料寫入規則。

證據：非空待辦被關閉及空待辦被重開兩個案例，修正前均失敗；修正後保留payload並恢復正確狀態。兩個案例同時確認再次執行零額外API寫入，無重複通知。
