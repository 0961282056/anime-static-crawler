# 資料查證與品質

每週工作負責核對所有已收錄季度及建立官方人工快照複查清單。AniList API 連線程式已退役，既有連結照常保留。公開集數與播出狀態仍由既有流程更新；每週核對只產生可追查的報告。

## 來源與引用原則

依精確卡片、原名、資料庫 ID 與季別／cour 核對；不模糊配對、不猜 ID，不將母條目、前季或不同版本的簡介套入卡片。只有缺漏且範圍吻合才補原文，已有可靠簡介不覆蓋。證據不足時保留缺漏、原因及後續查證方式。

人工修正同步登錄 `services/reviewed_*.json` 的精確規則，避免後續爬蟲覆寫或失去來源綁定。來源暫缺連結不表示既有衝突已解決；須有原相關季度、精確身分與一致明示連結的新證據。

每日來源重新擷取時，同一身分暫缺簡介會保留舊非空文字，不補造獨立署名或查證時間。原來源的非空文字更正仍可更新；作品身分改變時不沿用舊簡介，獨立署名與已審核範圍仍受原規則保護。

百科原文使用獨立 `provider=wikipedia`／`method=wikipedia_excerpt`，保存文章、固定修訂 ID／URL、修訂時間、貢獻者歷史、CC BY-SA 4.0 與變更說明，並在卡片及簡介視窗呈現。修訂時間與本次查證時間分開；周邊引用未實際讀取時，不冒稱已核對原始來源。模型與防覆寫範例見[維基百科補齊紀錄](wikipedia-fill-2026-10-19/README.md)。官方、Bangumi 與百科不得互相偽標。

## 使用方式

```bash
python manage.py source-audit
```

預設產生 `audit-output/source-audit.json` 與 `source-audit.md`，目錄已忽略。可用 `SOURCE_AUDIT_OUTPUT` 指定目錄，但不能設於公開 `dist` 內。需要 `requirements-canary.txt` 的既有依賴，不需要 Cloudinary 或 AniList 金鑰。

AniList API 客戶端、比較器及 `SOURCE_AUDIT_ANILIST_ENABLED` 開關已移除；舊環境留下 `true` 也不會啟用連線。這是退出該 API 路徑，不表示其 Cloudflare 403 已解除。

JSON 保留 schema 1 及相容欄位，固定記錄 `secondary_source.state=retired`、`reason=anilist_api_retired`；逐筆 `result=not_attempted`，觀察與嘗試／成功時間為空。摘要將可對應的 ID 數與本次要求／嘗試／觀察數分開，後三者固定為 0，不能算作查證成功。退役收據不列 GraphQL 請求網址；歷史報告仍保留原有取得方式與來源。

季度來源錯誤、既有連結衝突、官方快照到期及官方目錄更新失敗仍依原規則處理；API 退役本身不是問題解決證據，不關閉舊 Issue 或清除未送達持久待辦。保留 772 筆連結與精確來源綁定；1,378 筆可選未連結數照實記錄，停止主動補齊。先前設定與實作見[歷史索引](archive/README.md#事故與過渡操作)。

GitHub Actions 的 **Weekly Source Coverage and Cross-check** 每週一台北時間 10:30 執行，也可手動執行。Actions Summary 顯示摘要，完整 JSON 放於 `source-audit-<run_id>` artifact，保留 30 天。獨立的通知工作依報告建立 GitHub Issue，指派給儲存庫擁有者；可透過 repository variable `SOURCE_REVIEW_ASSIGNEE` 指定另一位有資格接受指派的使用者。未增加 Discord 或直接寄信功能；GitHub App／電子郵件的送達取決於使用者的 GitHub 通知設定。

## 收到通知後如何審核

Issue 會以中文列出作品、季度、目前已確認資料、來源差異、官方範圍與來源連結，並附核對執行連結；歷史第二來源案件保留原比較證據。直接在該 Issue 留言：

- **A：保留目前資料**，說明採用電視版、網路版或哪一季度的範圍。
- **B：建議修正**，提供正確值、版本範圍及官方證據網址。
- **C：證據不足**，回覆 `C 待查 2026-10-30`（換成你要複查的日期）。每天台北時間 11:00 檢查，到期後留言提及你一次；已關閉的 Issue 會重開。可再回覆新的 C 日期延期。較新的 A／B 回覆會取消舊 C 提醒；沒有日期不會自動提醒。只有指定審核者的回覆有效，實際排程可能受 GitHub 延遲影響。

留言不是自動修改指令。維護者確認回覆後，需把決定寫入範圍規則或資料修正，完成測試及資料 PR，再關閉 Issue。批准程式 PR 不代表批准所有資料差異。

以下情況才建立待辦：

| 類型 | 觸發條件 | 要做什麼 |
|---|---|---|
| 歷史第二來源總數差異 | 舊報告已有原文、類型、查證時間及範圍證據；退役後不產生新的 API 比較 | 保留原案件，取得新證據後依 A／B／C 回覆，不因 API 退役當成解決 |
| 作品連結衝突 | 同一精確作品身分在不同季度使用不同的明確 AniList ID | 確認季度、版本與正確連結 |
| 官方快照到期 | 到達既定人工複查期限 | 重新核對官方證據；到期不代表原資料錯誤 |
| 來源連線異常（維運） | 季度取得或官方目錄更新失敗；舊報告另保留歷史第二來源錯誤 | 維護者依實際來源核實恢復證據；使用者無需選擇集數 |

缺少可選連結、標題格式不同、尚未確認的預定總數、單純狀態不同或過舊的主來源，先留在報告，不直接變成使用者的集數裁決。來源異常另開一個維運 Issue，與資料審核分開。

同一問題沿用原 Issue；沒有新證據時不更新、不留言、不重複提醒。證據改變才留言通知並更新原 Issue，必要時重新開啟。核對時間或執行網址變更本身不算新證據。關閉的 Issue 若證據相同，不會重開。來源恢復或候選消失時不自動關閉舊 Issue，以免把部分查詢失敗誤當成問題已解決；維護者核實後手動關閉。

每次最多新增／更新或到期提醒 10 個 Issue；先處理到期提醒，再將維運問題優先、其餘依首次發現時間排序。超額候選先寫入一個未指派的 `[系統] 資料複查持久待辦` Issue，後續報告未再出現也不會遺失原證據。通知完成或取得明確解決證據才移除待辦；單純查詢失敗、證據過舊或候選消失不算解決。這個系統 Issue 不需要你審核或手動修改。壓縮狀態限 50 KB、解壓限 2 MB；損壞、超限或出現多個佇列時停止並報錯，保留既有資料。通知工作會查看開啟及已關閉的 bot Issue，最多讀取 1,000 筆儲存庫 Issue／PR；超出時停止並報錯，避免漏查造成重複建立。API 失敗不自動重試寫入。既有 Issue 證據改變時，先讀取最多 500 則留言；只有可信 bot 的最近一則同問題證據通知可判定是否已送出。若留言成功但回應或 Issue 回寫失敗，下次不重發同一通知，只補回證據與狀態，成功後才清除持久待辦。舊證據曾被通知、後來改變再回到原內容，仍視為新變更正常提醒。人類貼上的標記不作為送達依據；讀取失敗、格式不符或達分頁上限時停止，保留待辦，避免漏讀後重複發送。

查資料的工作只有 `contents: read`；獨立的通知工作才有 `issues: write`，只使用 GitHub 自動注入的短期 token，不需要新的個人 token 或正式爬蟲密鑰。通知只讀取同次執行的報告 artifact。

## 前後差異與處理規則

| 項目 | 原本 | 改善後 |
|---|---|---|
| 歷史季度 | 一般爬蟲主要更新近期季度 | 每週讀取所有本地已收錄季度的來源頁面，列出漏收、消失、改名、播出欄位與明確外部 ID 差異 |
| 人工快照 | 查證時間與範圍存在備註，需逐筆翻閱 | 依精確作品身分去重，未完結／未知每 7 天、已完結每 90 天排入複查清單；跨季副本取最舊成功查證時間 |
| 第二來源 | Bangumi API 與 Archive 能互相備援，但資料系譜相同 | AniList API 已退役，沒有新的第二來源 API 查證；既有參考連結與歷史比較保留 |
| 資料來源紀錄 | 部分方法、範圍在自由文字 | 每份報告逐筆列出 provider、scope、來源網址、成功查證、最後嘗試、未知欄位與原始備註 |
| 簡介等缺漏 | 無法從統計分辨為何缺少 | 報告區分來源本來缺少、來源有但尚未匯入、這次無法取得對應來源 |

季度來源必須全部卡片可解析且 ID 不重複，才進行該季集合比較。任何一張解析失敗，整季標示錯誤，避免把解析失敗當成作品刪除。即使來源真的不再列出作品，也只列為待查證，不自動刪除。一般季度寫入也逐一檢查舊卡片 ID；任一卡片消失便拒絕該季寫入、列出消失 ID 並保留原檔，即使總數未減少也不例外。確認移除時以附有來源證據的資料 PR 審查處理，日常爬蟲沒有略過此保護的開關。

季度核對每頁只嘗試一次，沿用 15 秒預設請求逾時，整個季度階段預算 600 秒；預算用完後，其餘季度標示未完成並保存報告。這與每日爬蟲的重試和集數更新預算分開，避免每週檢查影響正式資料更新。

季度比對使用已審查過的 parser，所以既有明確的 Bangumi ID 修正仍有效。它核對的是經既有規則處理後的來源，不是完全獨立的第二解析器。

AniList 只使用資料中已有、或當次季度頁面明確提供的連結。不進行名稱模糊搜尋。從來源補取連結時，卡片 ID、中文名、原文名必須完全符合既有身分，且來源的 Bangumi ID 不可與已知 ID 衝突（來源暫缺連結時保留既有 ID）；同一作品跨季出現不同 AniList ID 時直接列為衝突，不任選一個。新找到的連結僅存在報告，不改寫公開資料。

歷史 AniList API 的名稱、類型、日期與請求預算規則保留於固定版本，不再作為可啟用功能維護。來源總數或狀態一致，仍不能證明 TV、網路版、分割季度及特別篇範圍相同。

來源取得失敗時，報告保留其他成功季度／批次，失敗項目的成功查證時間為空；命令以非零狀態結束，Actions 仍保存部分報告。正常的資料差異不令命令失敗。此流程不刷新既有資料的 `checked_at`。

## 需要人工判斷的界線

維護者可先處理名稱格式、來源暫時失敗及既有範圍規則；使用者不需要逐筆審查報告。只有找不到既有規則可解釋的作品身分或集數範圍爭議，才整理「目前值、來源值、證據、建議」提出討論。

人工快照的複查期限是維護政策，不表示期限內必然最新。錢天堂已有專屬 NHK 完整目錄抽取器：每日爬蟲判斷到期後每七天核對一次，失敗隔一天重試。固定作品身分、讀完所有頁面、每個節目 URL 唯一且所有舊節目仍在，才更新已播數；不按標題去重、不計當日及未來節目，也不從目錄筆數推論總數或完結。單次最多 40 請求、階段預算 120 秒（最後一筆讀取可能超出），請求起點至少間隔 0.5 秒。缺頁、改版、舊節目消失或進度倒退時保留上次成功資料，記錄失敗嘗試時間並列入維運報告。其餘官方人工快照維持人工複查；單獨重跑本報告不刷新快照。

## 保留的限制

- 只檢查本地已收錄季度，不探索未知季度，也不證明原季度來源本身沒有漏作品。
- 不再進行 AniList API 查詢；總數不一致不會自動選較大值。
- 公開 JSON 新增可選的來源方式、來源快照日期及簡介來源；網站「集數來源與確認時間」分開顯示成功查證與最近嘗試、範圍說明及證據連結。舊資料無法確定 API／HTML／Archive 方法時明確標示未記錄，不把本次整理時間當作原始查證日期。
- 歷史 AniList 報告中的未來排程不等於已播證據；不從下一集時間或總集數推算已播進度。
- 每週報告只記錄來源觀察，不自動採用外部來源數字。明確連結可用 `update_episode_metadata.py --all --links-only` 預覽，加 `--write` 寫入；此流程拒絕重複卡片、名稱變更及已知 ID 衝突。每日集數更新可重用同次 Bangumi 回應補缺漏簡介，但須 ID、動畫類型與原文名相符；保留季數及副標題，只正規化字元格式，已有簡介不覆蓋。補入內容保留來源原文與取得方式／快照日期，原來源重新提供簡介時優先採用原來源。

## 產生離線品質證據

`python manage.py quality-evidence` 唯讀產生 `audit-output/quality/`，不請求外部來源、不需要 Cloudinary 或通知憑證。main 更新後的 **Quality Evidence and Trends** 工作會自動執行，artifact 保留 90 天。

## 統一證據格式

離線品質報表及每週來源核對都輸出 schema_version=1 的 `evidence.json`。每筆包含精確卡片／中文名／原名／Bangumi 身分、季度、欄位、來源網址、取得方法、計數範圍、內容 SHA256、原始檔 JSON pointer 及可重現的 evidence_id。

| 狀態／時間 | 意義 |
|---|---|
| observed / checked_at | 本次來源核對有成功觀察；比對有差異仍可為成功觀察，不表示資料應改寫 |
| failed / attempted_at | 本次確實開始請求但沒有完成查證，checked_at 為空 |
| not_attempted | 預算耗盡等原因未開始請求，不產生嘗試或成功時間 |
| retained / last_verified_at | 沿用公開資料已記錄的證據，不是本次重新查證 |
| unrecorded | 來源方式、日期或範圍未記錄，維持未知 |
| assembled_at | 整理檔案時間，不是查證時間 |
| source_snapshot_at | 原資料明確記錄的快照日期，沒有則留空 |

內容指紋針對 JSON 正規化後的欄位／比對結果；季度核對的 document_sha256 則是取得的 HTML 文件指紋。兩者不冒充已保存的原始 HTTP 回應。完整內容依 locator 回看同 artifact 的 source-audit.json 或 dist/data 快照；離線 bundle 另記錄資料是否符合 commit，以及保存檔案的逐檔 SHA256。尚未提交的資料不冒充 commit 版本。舊有人工證據文件仍是原始證據，不把整理日倒填為查證日。

每週核對仍是唯讀，既有通知工作不因新格式增加權限或改寫公開資料。來源失敗時，保留的 primary 舊成功時間與本次失敗／未嘗試分列。

## 品質歷史

`quality-trend.json` 從 Git 的 main 第一父系資料變更版本重建，依提交順序，保存每版原始數量與分母比率；`recorded_at` 是提交時間，不是來源查證時間。預設最近 120 個資料版本，可用 `QUALITY_HISTORY_LIMIT=1000` 擴大。截斷、淺層 clone、不相容版本都明列，不能當成完整歷史。

度量季度記錄而非推測去重作品：簡介／首播日／Bangumi／AniList 缺漏、集數 stale／conflict、未記錄取得方法或成功查證時間。`working_tree.issue_records` 可按季度及精確作品身分查缺漏；`change` 僅比較兩版相同身分，改名、換 ID、新增或移除另計，避免刪除作品被算成「修好」。沒有集數資料的舊版本視為查證時間缺漏，方法未知則只計已有集數欄位者。

`quality-trend.svg` 可直接以瀏覽器開啟，顯示簡介、AniList、集數查證時間的缺漏率；原始 JSON 含所有八項度量。artifact 到期後，完整 Git 歷史仍可重新產生。早期空季度保留為零筆；歷史結構無法讀取或身分重複會明列跳過，不套用今天的驗證或來源方法回寫舊資料。

歷次驗收數字見[歷史與證據索引](archive/README.md)，目前缺漏集中於[文件入口](README.md)，避免將舊快照當成即時統計。
